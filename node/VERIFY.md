# Node.js armv7 verification checklist

Run these on the device, in order, after `node/build.sh` produces
`out/node-22.23.4-armv7` and `node/make-deb.sh` produces the `.deb`.

**Nothing here has been run yet.** No armv7 Node binary existed when this
was written (2026-11-08). Every item below is a procedure, not a result.
When you do run it, do not edit this file to say "verified" — put the
outcome, with the date, in `DEVICE.md` (see the record format at the end).

Throughout, `node` means the wrapper at `/var/mobile/tools/node/bin/node`.
That matters: a bare `node.real` will be killed the moment V8 tries to JIT.

```sh
# one-time setup for a whole verification session
export PATH=/var/mobile/tools/node/bin:$PATH
mkdir -p /var/mobile/scratch/node     # DEVICE.md §9: scratch, not $HOME
cd /var/mobile/scratch/node
```

---

## 0. Before anything else: did the file survive the transfer?

`rc=137` (SIGKILL) with **empty stdout and stderr** means the kernel killed
an unsigned or corrupt Mach-O during `exec`, before `main()`. Per DEVICE.md
§10, the operational rule is: **treat rc=137 as "signature missing, corrupt,
or not-yet-transferred" — verify the transfer before blaming the signer.**
Do not re-sign as a first response; §10 refuted the "sign twice" rule and
the one kill it came from was never reproduced (16/16 single-signed runs
passed).

```sh
# on the host, after copying the .deb across:
sha256sum out/node4_22.23.4-1_iphoneos-arm.deb
# on the device:
md5 /var/mobile/scratch/node/node4_22.23.4-1_iphoneos-arm.deb   # if md5 exists
```

If the two do not match, stop — the rest of this file is meaningless.

```sh
# confirm the staged copy really carries a signature
ldid -e /var/mobile/tools/node/bin/node.real >/dev/null && echo "signature present"
# ldid -e exits 0 ONLY on a signed file (checked on the host: exit 1 before
# ldid -S, exit 0 after). It is a weak check -- it says "there is a
# signature", not "the signature is valid". Executing the binary is the only
# real test, which is item 1.
```

Also confirm `node` is the *wrapper*, not the engine:

```sh
head -c 4 /var/mobile/tools/node/bin/node        # want: #!/b
head -c 4 /var/mobile/tools/node/bin/node.real   # want: binary garbage / Mach-O magic
```

If those two are the same, the package is wrong: `node` must be the shell
wrapper from `jitless-wrap.sh` and `node.real` must be the Mach-O. Running
the engine directly is exactly the case that gets killed.

---

## 1. Startup smoke — does it run at all?

The single most important test. If this fails, nothing below is worth
running.

```sh
node -e 'console.log(process.arch)'
```

**Expect `arm`.** Not `armv7`, not `ia32` — Node reports the `--dest-cpu`
value, which is `arm` for both armv6 and armv7.

```sh
node --version          # expect v22.23.4
node -p 'process.platform'   # expect darwin
```

Then confirm the wrapper put jitless in place without the user asking:

```sh
node -e 'console.log(process.execArgv)'
```

**Expect `[]`.** This is the interesting one. `--jitless` was injected via
`NODE_OPTIONS`, and `process.execArgv` reflects the *command line*, not the
environment — so an empty array here is correct and is evidence the wrapper
worked the intended way. If you see `[ '--jitless' ]`, then someone passed
it on the command line, which still works but is not the packaging default.

```sh
# the direct, unambiguous check that the flag is actually in force:
NODE_OPTIONS=--jitless node -e 'console.log(1)'
```

**Expect `1`.** This is called out separately because it is the only item in
this file that tests the jitless mechanism end to end on real hardware.

## 2. JIT is really off

Item 1 shows the flag is *passed*. This shows it *took effect*. There are
three independent angles; run at least the first two.

**(a) The counter-argument guard — V8 must agree jitless is on.**

```sh
node --jitless --v8-options 2>&1 | grep -A1 'jitless'
```

There is no clean `process.*` API that reports jitless state, so this is
indirect. A stronger version, if `--allow-natives-syntax` works:

```sh
node --allow-natives-syntax -e 'console.log(%GetOptimizationStatus(function f(){}))'
```

> **NOT VERIFIED, and possibly wrong.** `--allow-natives-syntax` is a V8
> flag and is *not* in the `NODE_OPTIONS` allow-list, so it must be passed
> on the command line. Whether it is compiled in — and whether
> `%GetOptimizationStatus` exists as a runtime function in this V8 build —
> was not checked. If it errors, that is a finding, not a failure; record it
> and move on. Do not paper over it.

The intended reading: in jitless mode the function should never reach an
optimized tier. Any status indicating optimized code under jitless is a
contradiction worth chasing.

**(b) Executable memory should not be there.** This is the angle that
matches the actual failure mode, and `lsof` cannot see it — but the process
can report its own mappings, and the device has no `/proc`. What it does
have is the ability to ask the kernel through `mach_vm_region`, which is
what a small probe program would do (see `~/scratch/node-research/probes/`
for the existing pattern). **Not implemented for Node** — listed here so the
gap is visible rather than implied.

What the existing standalone probe already established on this device
(`~/scratch/node-research/probes/jit.c`, and see `DEVICE.pending.md` §12.1):

- RWX at `mmap` **works** — the probe writes an ARM stub and it executes,
  printing `JIT OK returned 42`;
- `MAP_JIT` (`0x800`) **fails with `EINVAL`**;
- signing a binary with the `platform-application` entitlement **does not
  help** — the kernel kills it (rc=137, empty output, before `main()`);
- with those facts, V8's `kMmapFd = VM_MAKE_TAG(255)` pseudo-fd — which
  raised **SIGSYS** on iOS 10 — was patched to `-1`.

So the interesting question for Node is not "does the kernel refuse
executable mappings in general" (it does not) but "does jitless keep V8 from
ever asking for one".

**(c) The practical test — a workload that would JIT.**

```sh
node -e 'function f(x){return x*2} for(let i=0;i<1e6;i++) f(i); console.log("survived")'
```

**Expect `survived` and no kill.** A hot loop is what triggers tier-up in a
normal build. This does not *prove* jitless is on, but it does prove the
process is not dying the way an un-jitless one would, which is the thing
that actually matters for usability.

## 3. Module system

```sh
node -e 'const fs=require("fs"); console.log(typeof fs.readFileSync)'
node -e 'const c=require("crypto"); console.log(c.createHash("sha256").update("abc").digest("hex"))'
```

**Expect `function`** and
**`ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad`**
(the SHA-256 of `abc` — a fixed value, so this doubles as a crypto
correctness check; a wrong digest means a broken OpenSSL linkage, not a
broken script).

```sh
node -e 'console.log(require("os").arch(), require("path").join("a","b"))'
```

Then ESM, which exercises a different loader path:

```sh
echo 'import fs from "node:fs"; console.log("esm ok", typeof fs.readFileSync)' > t.mjs
node t.mjs
```

**Expect `esm ok function`.** If ESM fails while CJS works, that is a
loader/module-resolution problem specific to this port and worth recording
separately.

## 4. Network — an HTTP server plus a client

Node's networking is libuv + c-ares, both of which needed device-specific
headers (DEVICE.md §11.1). This is where a wrong header shows up as a
runtime failure rather than a compile error.

Port choice: **`49178` is taken** (verified on device: `homed` listens
there on TCP). 22 and 22226 are dropbear/OpenSSH. Use **8787**, which
`lsof -nP -iTCP -sTCP:LISTEN` showed free on 2026-11-08.

```sh
# terminal 1 (or background it)
node -e '
const http = require("http");
http.createServer((req,res)=>{res.end("hello from node "+process.arch)})
    .listen(8787, "127.0.0.1", ()=>console.log("listening"));
'
```

```sh
# terminal 2 — the device's own curl 8.16.0
curl -s http://127.0.0.1:8787/
```

**Expect `hello from node arm`.**

```sh
# confirm the socket is really Node's, not something stale
/var/mobile/tools/lsof -nP -i :8787
```

Then outbound DNS + TLS, which is a much harder test of the same stack:

```sh
node -e '
require("https").get("https://nodejs.org/dist/index.json", r => {
  console.log("status", r.statusCode);
  r.resume(); r.on("end", ()=>console.log("done"));
}).on("error", e => console.log("ERR", e.message));
'
```

> **Expect this to be slow.** The README records TLS 1.2 handshakes at
> ≈6 s on this device for curl, and Node has no session cache help here.
> A 30 s timeout is reasonable. **Not verified** whether Node's bundled
> OpenSSL 4.0.3 finds a CA store on iOS 10 — Node does not use
> `/etc/ssl/cert.pem` the way curl does. If this fails with a certificate
> error while a raw `http://` fetch succeeds, the cause is the trust store,
> not the network stack, and the fix is `NODE_EXTRA_CA_CERTS`.

A plain-HTTP outbound fetch separates "networking works" from "TLS trust
works":

```sh
node -e 'require("http").get("http://nodejs.org/", r=>{console.log(r.statusCode); r.resume()})'
```

## 5. Buffers and timers

```sh
node -e 'console.log(Buffer.from("aGk=","base64").toString())'      # expect hi
node -e 'console.log(Buffer.alloc(4).length, Buffer.from([1,2,3]).toString("hex"))'
node -e 'let n=0; const t=setInterval(()=>{ if(++n===3){clearInterval(t); console.log("ticks",n)} },100)'
node -e 'setTimeout(()=>console.log("timed out"), 50)'
```

**Expect `hi`, `4 010203`, `ticks 3`, `timed out`.** These exercise the
event loop, which is also what the HTTP test does — if timers work but HTTP
does not, the problem is in the socket layer, not the loop.

A more demanding one, since it touches libuv's thread pool:

```sh
node -e 'const fs=require("fs"); fs.writeFileSync("/var/mobile/scratch/node/w.txt","x");
         fs.readFile("/var/mobile/scratch/node/w.txt",(e,d)=>console.log("async",d.toString()))'
# and the threadpool path:
node -e 'require("crypto").pbkdf2("p","s",1000,32,"sha256",(e,k)=>console.log("pbkdf2",k.length))'
```

**Expect `async x` and `pbkdf2 32`.** `pbkdf2` with an explicit callback runs
on the libuv thread pool; if `uv_thread_create` is broken on this device the
process hangs here rather than erroring, so run it with a timeout.

## 6. CPU information

```sh
node -e 'console.log(JSON.stringify(require("os").cpus(), null, 1))'
```

This one has a specific expected failure mode, established from the source
rather than guessed. `deps/uv/src/unix/darwin.c:195` reads the CPU model
with:

```c
if (sysctlbyname("machdep.cpu.brand_string", &model, &size, NULL, 0) &&
    sysctlbyname("hw.model", &model, &size, NULL, 0)) {
  return UV__ERR(errno);
}
```

On this iPad, **`machdep.cpu.brand_string` does not exist** — verified on
the device with `/usr/sbin/sysctl -n machdep.cpu.brand_string`, which
returns `machdep: class is not implemented`. So the fallback to `hw.model`
is the path that runs, and `hw.model` returns **`P101AP`** (also verified;
note `uname -m` says `iPad3,4` and `hw.model` says `P101AP` — they are not
the same string, and libuv uses the latter).

So: **`os.cpus()[0].model` is expected to be `P101AP`.** If you get the
market name (`iPad3,4`) instead, the first sysctl succeeded and this note is
stale.

`os.cpus().length` should be **2** (`hw.ncpu` = 2, verified on device).

```sh
node -e 'const c=require("os").cpus(); console.log(c.length, c[0].model, c[0].speed)'
```

`speed` is expected to be **0**: libuv reads `hw.cpufrequency`, which the
device reports as `No such file or directory` (verified), and the
hard-coded 2400 MHz fallback in that source file is guarded by a comment
about `CPU_TYPE_ARM64` — which this is not. A speed of 0 here is therefore
correct behaviour for an armv7 iOS device, not a bug. **Not verified** that
the guard really does exclude armv7 in this libuv version; it was read, not
executed.

Also worth capturing once, since these are the machine's real limits:

```sh
node -e 'console.log(require("os").totalmem(), require("os").freemem(), require("os").endianness())'
```

`hw.memsize` = 1034944512 (≈987 MiB) and `hw.pagesize` = 4096 were verified
on the device with `sysctl`. `endianness()` should be `LE`.

## 7. npm

npm is *not* built into the binary (`--without-npm`); it is packaged
separately. If it was staged:

```sh
npm --version
npm config get prefix
```

> **NOT VERIFIED.** npm 10.9.9 requires Node `^18.17.0 || >=20.5.0` — the
> version check is from `deps/npm/package.json`, read directly, and v22.23.4
> satisfies it. What was *not* checked is whether npm actually functions on
> a jitless armv7 build: npm is ~20 MB of JavaScript with a heavy
> dependency graph, and it is the single most likely thing to be slow
> enough to be unusable rather than broken. Time `npm --version` first — if
> that takes minutes, the answer is "installs work, use is painful", which
> belongs in DEVICE.md as a number, not an adjective.

## 8. What "good" looks like, and what to do when it is not

| symptom | most likely cause | where to look |
|---|---|---|
| `rc=137`, empty stdout **and** stderr | unsigned/corrupt Mach-O killed at `exec` | §0 above; DEVICE.md §10 — check the transfer first, **do not re-sign** |
| `Killed: 9` after startup, once code runs | JIT allocation reached the kernel | wrapper bypassed — confirm `bin/node` is the shell script, not the engine |
| works bare, dies under a script | same as above, but triggered later | run with `NODE_OPTIONS=--jitless` explicitly to confirm |
| `Cannot allocate memory` | a hand-parsed kernel struct with the wrong layout — the lsof 4.78 disease (README) | check which sysroot header is involved |
| hangs, no output, no kill | libuv thread pool (`uv_thread_create`) — see §5 pbkdf2 | `~/scratch/node-research/probes/atfork-probe` |
| wrong value, no error | a Darwin ABI struct that is a few bytes off | DEVICE.md §11.3 is the list of ones already caught this way |

## 9. Record format for DEVICE.md

When this is done, add a numbered section to `DEVICE.md`, in the style of
§8 (lsof). It is gitignored, so it is where the *device-specific* results
belong — the numbers, the surprises, the things that are true of this iPad
and nowhere else. Include:

* the date and the exact version string (`node --version` output);
* the jitless mechanism as it behaved *here*, including whether
  `process.execArgv` was empty as predicted in §1;
* real timings, not impressions — startup for `node -e ''`, and the jitless
  cost measured against the same script with the flag omitted on a machine
  that can JIT, or at minimum a wall-clock for a fixed loop;
* `os.cpus()` output verbatim, since §6 above predicts it and a prediction
  that was never checked is worse than no prediction;
* anything in this file that turned out to be **wrong**, kept rather than
  quietly deleted — the README's own history (the `--jitless`-adjacent
  "sign twice" episode, §10) exists precisely because a confidently-written
  wrong rule cost real effort.
