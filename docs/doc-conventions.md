# 专项文档写作规范

> 本仓库 `docs/` 下每个移植包一份 `docs/<pkg>.md`。本文规定这些文档
> 该写什么、不该写什么，以及和 `build.sh` 注释的分工。
> 建新包文档前先读本文。

## 1. 两份材料的分工（**最重要的一条**）

| 材料 | 定位 | 写什么 |
|---|---|---|
| `<pkg>/build.sh` 注释 | **施工日志** | 逐步推理、每次试错的原始现场、为什么否掉某个方案 |
| `docs/<pkg>.md` | **产品说明书 + 踩坑索引** | 结论、要点、坑 → 修法映射、设备侧用法 |

**不要把 build.sh 注释抄进 docs**。那会造成两处维护，且 docs 会被
施工细节淹没。正确的做法是**提炼成结论**，细节用一句
「详见 `<pkg>/build.sh`」指过去。

判断标准：**读者不看源码，能不能知道这个包是什么、怎么用、踩过什么坑、
现在什么状态？** 能，就写对了。

## 2. 必备结构

按包情可调整，但这几节通常都要有：

```markdown
# <包名> <版本> 移植专项（armv7 iOS 10.3.3）

> 包：`<deb 名>` · <一句话状态>
> 构建脚本注释即详细文档：`<pkg>/build.sh`（N 行注释）
> 本文记录**状态、用法、坑与结论**；细节指向 build.sh，不重复。

## 1. 状态
（表格：版本 / 包名 / 安装路径 / 验收结论）

## 2. 依赖链
（如果有多层依赖；没有就省略）

## 3. 坑列表          ★ 最有价值的部分
（表格：坑 → 要点/修法。这是文档存在的主要理由）

## 4. 设备侧用法 / 注意事项
（怎么跑、怎么停、有哪些预期内的"异常"）

## 5. 相关文件
（表格：build.sh / make-deb.sh / patch / 配置模板）
```

## 3. 硬性要求

1. **中文正文**（技术名词、代码、报错原文保留英文）。
2. **不编造**。素材里没有的信息不要写——特别是**验收结论**：
   只有构建信息、没有设备实测证据时，写「构建完成」，
   **不要写「验收通过」**。本仓库历史上出现过假验收记录，
   这类错误代价极高。
3. **脱敏**（要提交到 git）：
   - 内网 IP、真实主机名、密码 **不得出现**；设备统一写 `<device>`
   - 账号、密钥路径不出现
   - `$HOME`、`~/ios-tool` 这类本地约定路径可以保留（非机密）
   - 真实地址等私有信息放 `DEVICE.md`（**gitignored**）
4. **引用通用规则用章节号**：很多坑是跨包通用的，已在
   `docs/toolchain.md` 里编号（如 §2 归档格式、§8 dynamic_lookup 恒真探针、
   §9 configure 探测欺骗、§19 原子对齐陷阱）。docs 里用
   「见 `docs/toolchain.md` §8」指过去，不要重复展开。
5. 标题格式：`# <包名> <版本> 移植专项（armv7 iOS 10.3.3）`

## 4. 写文档时的取材顺序

1. `<pkg>/build.sh` 的注释块（信息密度最高）
2. `<pkg>/make-deb.sh`（部署布局、postinst/prerm、双签名）
3. `<pkg>/patch-*.py`、配置模板（`*.conf`、`*.plist`）
4. `docs/porting-backlog.md` 里该包的历史条目
5. `docs/toolchain.md` 相关章节
6. **设备实测**（能连设备时）——比任何注释都权威

## 5. 反面例子（不要这样写）

- ❌ 把 build.sh 的 30 行墙列表原文贴进 docs
  → ✅ 提炼成「坑 → 修法」表格，细节指向 build.sh
- ❌ 写「验收通过」但其实只编出来了没上设备
  → ✅ 写「构建完成，设备验收待补」
- ❌ 写「8 字节原子静默失败」（未经验证的转述）
  → ✅ 写实测现象 + 探针出处（见 `docs/toolchain.md` §19 的修正记录：
     早期文档写错了根因，后来靠设备探针推翻）
- ❌ 记录里出现真实 IP
  → ✅ `<device>`
